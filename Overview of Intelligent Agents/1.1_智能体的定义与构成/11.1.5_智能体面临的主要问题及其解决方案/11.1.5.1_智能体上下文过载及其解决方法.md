**上下文过载（Context Overload，常与“上下文腐化 Context Rot”或“中间遗忘 Lost in the Middle”相关联）**是指在大语言模型（LLM）或智能体（Agent）的输入上下文窗口（Context Window）中塞入了过多、冗余、噪声高或相互冲突的信息，导致模型**推理准确率下降、关键信息被忽略、幻觉增加、延迟飙升且成本恶化**的现象。

核心误区在于把“上下文窗口变大（如 128K、1M 甚至更长）”**等同于**“模型能有效利用所有塞进去的 Token”。实际上，“能装下”不代表“能看清并正确推理”。

下图中展示了一条典型的 **U 型注意力曲线（Lost in the Middle）**：输入序列开头的指令与末尾的最新输入更容易获得较高关注，而处于中间长段位置的检索文档或历史信息，更容易出现关注度下降与漏看。

## 一、 上下文过载为什么会发生？

在多轮对话、RAG 检索和智能体循环中，上下文很容易在不知不觉中膨胀：

1. **多轮智能体轨迹堆积**：ReAct 或多步规划智能体在执行任务时，每一步的 `Thought`、工具入参以及冗长的工具返回结果（如整页网页 HTML、大段代码文件、长日志）都不断追加进历史消息列表。
2. **过度检索（Over-Retrieval）**：RAG 阶段盲目召回大量 Top-K 文档片段，其中包含大量重复段落、低相关度背景甚至互相矛盾的旧版本说明。
3. **臃肿的系统提示词与工具定义**：把几十个工具的详细 Schema、冗长规则和海量 Few-Shot 示例全量塞进 System Prompt，挤占了有效注意力预算。
4. **噪声与冲突信息混入**：历史对话中的过期指令、错误尝试记录或无关背景与当前目标交织，干扰模型的意图对齐与因果推理。

## 二、 上下文过载带来的典型表现

当系统出现上下文过载时，通常会表现出以下特征：

* **注意力稀释与“中间遗忘”**：关键约束、数字细节或检索到的核心证据恰好落在长上下文中段时，模型容易漏用或误用。
* **指令遵循退化与行为漂移**：长对话后期，模型可能忽略早期设定的输出格式、安全边界或角色限制，甚至在智能体循环中重复无效动作或陷入死循环。
* **幻觉与关联错误增多**：无关信息过多时，模型更容易把不相关的片段强行拼凑出看似合理的回答。
* **首字延迟（TTFT）与 Token 成本上升**：预填充（Prefill）阶段需要处理海量 Token，不仅拉长响应时间，还会显著增加推理成本（即使有 KV Cache 复用，新增长输入与多轮累计依然昂贵）。

## 三、 如何缓解与治理上下文过载？

工程上通常通过上下文工程（Context Engineering）把“塞得越多越好”转变为“只给最相关、最精炼的必要信息”：

| 治理策略 | 具体做法 | 作用 |
| --- | --- | --- |
| **检索精炼与重排** | 结合混合检索与 Rerank 过滤低相关切片，控制注入上下文的文档数量与长度 | 减少无关背景与噪声干扰 |
| **工具输出截断与摘要** | 工具返回长文本或长日志时，先在工具层提取关键字段/摘要或分页读取，再回传给模型 | 防止单次工具调用撑爆上下文 |
| **短期记忆压缩与状态外置** | 定期将早期对话或已完成子任务压缩为结构化摘要；将中间变量、草稿存放在外部 State 或文件中，按需读取 | 维持长程任务连贯性并控制历史长度 |
| **提示词与工具按需加载** | 精简 System Prompt，按任务阶段或路由结果动态挂载所需工具与规则 | 降低指令冲突与工具选择混淆 |
| **子任务隔离（Sub-Agent / 上下文隔离）** | 将高噪声的探索性子任务（如读大量文件、做深度调研）交给独立子智能体执行，只向主流程回传精炼结论 | 保护主智能体上下文窗口的信噪比 |
