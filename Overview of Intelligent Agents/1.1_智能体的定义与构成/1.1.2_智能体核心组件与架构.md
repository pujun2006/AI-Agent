现代智能体（尤其是基于大语言模型的 AI Agent）在工程实现上通常围绕“大语言模型核心（LLM Core） + 规划（Planning） + 记忆（Memory） + 工具（Tools） + 感知与执行接口（Perception & Action）”构建。这一架构范式最早由 Lilian Weng 等研究者系统总结，并已成为主流 Agent 框架（如 LangGraph、AutoGen、LlamaIndex 等）的设计蓝本。

## 一、 智能体的五大核心组件

### 1. 基础模型核心（Brain / Foundation Model）

* **定位**：智能体的中央控制器与推理引擎，通常由具备强指令遵循与工具调用（Function Calling）能力的 LLM 或多模态大模型（VLM）担任。
* **职责**：理解系统提示词（System Prompt）设定的角色与约束，综合当前上下文、记忆与工具返回结果，输出下一步的思考过程（Thought）、工具调用指令或最终答复。
* **路由优化**：复杂架构中常采用**模型路由（Model Routing）**，将简单的意图识别分发给轻量小模型，将复杂规划与代码生成分发给高推理能力大模型，以平衡延迟与成本。

### 2. 规划与推理模块（Planning & Reasoning）

规划模块决定智能体“如何把大目标拆解为可执行步骤，并在出错时修正路径”，主要包含两类机制：

* **任务分解（Task Decomposition）**：
* **思维链（CoT, Chain-of-Thought）**：引导模型在输出动作前逐步推演逻辑。
* **思维树（ToT, Tree-of-Thoughts）与图搜索**：在关键决策点探索多条推理分支，评估各路径可行性后择优推进。
* **先规划后执行（Plan-and-Solve）**：先生成全局子任务列表（DAG 有向无环图或步骤清单），再逐项执行并动态更新进度。


* **自我反思与纠错（Self-Reflection & Refinement）**：
* 典型模式如 **ReAct（Reasoning + Acting）** 与 **Reflexion**。智能体在每次执行工具后观察环境反馈（Observation）；若出现报错、检索为空或结果不符预期，则分析失败原因并调整参数或切换工具重试。



### 3. 记忆系统（Memory）

记忆模块使智能体能够跨越单次推理步甚至跨会话保持状态一致性：

* **短期记忆（Short-Term / Working Memory）**：
* 依托模型的上下文窗口（Context Window）实现，记录当前任务的对话历史、中间推理轨迹（Scratchpad）以及本轮已调用工具的输入输出。
* **工程管理策略**：当任务步数增多导致上下文膨胀时，需引入滑动窗口截断、历史摘要压缩（Summarization）或关键状态提取，防止注意力分散与 Token 溢出。


* **长期记忆（Long-Term Memory）**：
* 依托外部存储系统实现跨会话持久化，通常结合**向量数据库（Vector DB，如 FAISS、Milvus、Qdrant）**、关系型数据库与知识图谱。
* **细分类型**：包括**语义记忆**（领域文档与事实知识，即 RAG 检索库）、**情景记忆**（过往成功/失败的任务轨迹案例，用于 Few-Shot 经验复用）和**程序性记忆**（固化的工作流模板与用户偏好设置）。



### 4. 工具与行动模块（Tools & Action Execution）

工具突破了大模型参数知识静态化、不擅长精确计算与无法直接操作外部系统的局限：

* **工具类型**：
* **信息获取类**：搜索引擎、网页抓取器、数据库查询接口（Text-to-SQL）、知识库检索器。
* **计算与代码执行类**：Python 沙箱代码解释器、数学计算引擎、数据分析脚本。
* **系统与业务操作类**：REST/GraphQL API、文件系统读写、Git 操作、邮件/日历/办公软件控制、浏览器自动化（GUI/DOM 操作）。


* **标准化协议**：现代架构普遍采用 **Function Calling（函数调用）** 与 **MCP（Model Context Protocol，模型上下文协议）**，通过标准化的 JSON Schema 描述工具名称、功能说明与参数类型，使模型能动态发现并安全调用外部能力。

### 5. 感知与环境接口（Perception & Environment Interface）

* **多模态感知**：将文本、图像、音频、视频、UI 截图、传感器日志或结构化事件流统一编码为大模型可理解的表征。
* **环境执行器与沙箱**：负责安全地执行模型生成的动作（如在隔离 Docker 容器中运行代码），并将执行状态、标准输出或错误堆栈格式化回传给感知层。

## 二、 智能体的典型系统架构模式

在实际工程落地中，上述组件通常按照以下几种主流架构模式组织编排：

| 架构模式 | 核心工作机制 | 适用场景 | 优缺点权衡 |
| --- | --- | --- | --- |
| **1. 单体循环架构（ReAct Loop）** | 采用 `思考(Thought) → 行动(Action) → 观察(Observation)` 的单循环不断迭代，直至满足终止条件 | 通用问答、轻量级检索分析、步骤不固定的探索性任务 | 结构简单、灵活性高；但长链路下易陷入死循环或上下文膨胀 |
| **2. 规划-执行解耦架构（Plan-and-Execute）** | 由“规划器（Planner）”先生成完整子任务队列，再由“执行器（Executor）”逐步调用工具完成，必要时触发重规划 | 深度研究报告生成、复杂数据处理、多步骤软件开发任务 | 全局视角更清晰、可减少大模型反复规划的开销；但对初始拆解质量依赖较高 |
| **3. 状态机与工作流图架构（State Graph / Workflow）** | 将业务流程抽象为有向图（节点为 LLM 或工具调用，边为条件路由与循环控制），显式管理全局状态（State） | 企业级生产系统、高可靠性审批/客服流、需确定性约束的任务 | 可控性强、易于调试与接入人工审批（Human-in-the-Loop）；前期编排开发成本较高 |
| **4. 多智能体协同架构（Multi-Agent System）** | 拆分为多个具备独立角色、提示词与工具权限的智能体（如产品经理、程序员、测试员），通过主管路由（Supervisor）或消息总线协作 | 大型代码库工程、复杂模拟推演、需要多视角交叉审核的任务 | 职责隔离清晰、单个智能体上下文更干净；通信开销大、协调与调试复杂度高 |

## 三、 完整运行生命周期（数据流闭环）

当用户向一个生产级智能体下达复杂指令时，底层架构通常按以下 6 个阶段运转：

1. **输入解析与上下文装配**：感知模块接收用户输入，系统同时从长期记忆中检索相关的用户偏好、历史经验与背景知识，组装初始 Prompt。
2. **意图评估与任务规划**：核心 LLM 判断任务是否可直接回答；若需多步处理，则生成子任务计划或首步推理思考。
3. **工具选择与参数生成**：模型根据工具描述（Schema）匹配最合适的工具，输出结构化的调用请求（如 JSON 格式的函数名与参数）。
4. **沙箱执行与权限校验**：执行引擎校验调用权限（高危操作触发人工确认），在隔离环境中运行工具并捕获返回结果或异常信息。
5. **状态更新与自我反思**：将工具返回结果写入短期记忆；模型评估当前进度是否达成目标——若未达成或发生错误，则修正策略并回到第 2 或第 3 步循环。
6. **结果汇总与记忆沉淀**：所有子任务完成后，整合信息生成最终输出；后台异步提炼本次任务的关键经验或用户新偏好，写入长期记忆库供未来复用。
