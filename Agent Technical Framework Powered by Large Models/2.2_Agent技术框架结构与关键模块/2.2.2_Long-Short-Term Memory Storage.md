Long-Short-Term Memory Storage.py代码实现了一个**融合“短/长期记忆 + 外部工具调用 + 本地微调语言模型”的金融客服智能体原型（`FinancialAgent`）**。它将前面讨论的“感知—决策—执行”闭环与“记忆模块”落到了一个可运行的 Python 脚本中：遇到账单查询类请求时路由到模拟外部接口获取结构化账单数据；遇到通用金融概念提问时调用本地中文 GPT-2 模型生成续写回答，并将每次交互记录持久化写入 SQLite 数据库。

---

### 一、 整体架构与运行主线

1. **`AgentMemory`（记忆系统）**：用内存字典维护当前会话状态（短期记忆），用 SQLite（默认 `customer_memory.db`）持久化客户历史问答记录（长期记忆）。
2. **`FinancialTools`（工具库）**：提供静态方法 `query_credit_card_bill(account_id)` 模拟外部账单查询接口。
3. **`FinancialAgent`（智能体核心大脑）**：负责意图路由、调用工具或大模型生成回复，并协调读写记忆。
4. **交互演示（`__main__`）**：依次模拟“查信用卡账单”与“金融知识问答”，最后读取并打印 SQLite 中的历史记录。

---

### 二、 分模块详细解析

#### 1. 记忆系统（`AgentMemory`）

* **短期记忆（`self.short_term_memory`）**：
* 初始化了 `"account_id"`、`"last_intent"`、`"current_step"` 三个键值，用于保存当前会话上下文状态。
* 提供了 `update_short_term` 和 `get_short_term` 做读写封装。当前代码中已实际使用 `"account_id"` 与 `"last_intent"`，`"current_step"` 则作为预留状态字段尚未被赋值。


* **长期记忆（SQLite）**：
* `_init_db()` 在表不存在时创建 `customer_history` 表，包含自增主键 `id`、`customer_id`、`query`、`agent_response` 以及默认当前时间的 `timestamp`。
* `save_long_term` 负责把每轮 `(customer_id, query, response)` 插入数据库并提交事务（`commit()`）。
* `get_long_term_history` 按 `customer_id` 过滤、按 `id DESC` 倒序取最近 `limit` 条（默认 `3` 条）记录。



#### 2. 工具库（`FinancialTools`）

* `query_credit_card_bill(account_id)` 使用 `@staticmethod` 封装，无需实例化即可直接调用。
* 内置了 `"12345678"`（未还款）和 `"88888888"`（已还清）两组模拟账单数据；查不到账号时返回 `None`，由上层决定兜底话术。

#### 3. 智能体核心大脑（`FinancialAgent`）

* **初始化（`__init__`）**：
* 绑定 `customer_id` 并立即写入短期记忆 `account_id`。
* 尝试从 `model_path`（默认 `./finetuned_gpt2`）加载此前微调好的分词器与 `GPT2LMHeadModel`；若加载失败（例如目录不存在或权重损坏），自动回退到基础模型 `"uer/gpt2-chinese-cluecorpussmall"`，并确保 `pad_token` 已对齐到 `eos_token`。


* **意图识别路由（`_intent_recognition`）**：
* 采用规则关键词匹配：只要 `user_query` 包含 `"账单"`、`"欠款"` 或 `"还款"` 之一，就返回 `"QUERY_BILL"`，否则归为 `"GENERAL_FINANCE_QA"`。这是一种轻量、低延迟、可预测的工程路由方式。


* **大模型生成（`_generate_llm_response`）**：
* 将 `prompt` 编码为 PyTorch 张量后调用 `model.generate(...)`，采用 `do_sample=True`、`top_k=30`、`top_p=0.85`、`temperature=0.7` 与 `repetition_penalty=1.3` 控制生成多样性并抑制重复。


* **消息处理主流程（`handle_message`）**：
1. 识别意图并更新短期记忆中的 `last_intent`。
2. 分支执行：
* `"QUERY_BILL"`：从短期记忆读取 `account_id`，调用 `FinancialTools.query_credit_card_bill` 拼装格式化账单文本；若无记录则返回提示信息。
* `"GENERAL_FINANCE_QA"`：调用 `_generate_llm_response(user_query)` 生成回答。


3. 调用 `self.memory.save_long_term(...)` 将本轮交互写入长期记忆并返回 `response`。

### 四、 潜在缺陷与工程改进方向

1. **长期记忆未真正参与当前推理上下文**：虽然 `get_long_term_history` 已经写好并在末尾打印了历史记录，但在 `handle_message` 处理新消息时并没有把历史记录或用户画像注入到意图判断或大模型提示词中，属于“只写不读进推理链路”。
2. **关键词路由容易误判与覆盖不足**：简单 `in` 匹配在面对复杂表达（例如“我不想看账单，帮我解释什么是复利效应”包含“账单”却不是查账单，或“信用卡额度/逾期利息怎么算”）时容易分流不准。后续可升级为分类器、语义路由或 LLM 结构化工具调用（Function Calling）。
3. **生成模型偏重“续写”而非“问答”**：GPT-2 类因果语言模型直接把 `user_query` 当作前缀续写，适合 `"债券投资的特点是"` 这类补全句式，但遇到问句时可能只是顺着句子接话，未必能给出规范的问答结论；结合指令微调或 Prompt 模板会更稳。
4. **数据库与并发/设备细节**：
* `sqlite3.connect(db_path)` 在多线程 Web 服务场景下可能遇到跨线程连接限制（可按需评估 `check_same_thread` 或连接管理策略），并在程序结束时注意关闭连接（`close()`）。
* `_generate_llm_response` 中 `inputs = self.tokenizer(prompt, return_tensors="pt")` 未显式 `.to(self.model.device)`，若未来把 `model` 放到 GPU 上，输入张量与模型不在同一设备时会报错。
