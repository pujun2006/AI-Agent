Conditional Reasoning and Decision-Making Chains.py代码实现了一个**基于 `LangGraph` 状态图与结构化输出的动态条件决策系统**（以信贷咨询、投诉分流与检索质量自检重检为例）。它将原本固定顺序或静态分支的链升级为“意图分流 → 检索评估 → 自动改写重试 → 有界收敛生成”的闭环状态机。

---

## 一、 整体图拓扑与动态流转

系统围绕共享状态 `DecisionState` 运行，节点与条件边决定了请求在动态环境下的走法：

```text
START
  │
  ▼
classify_intent (意图识别 + 提炼标准化检索词 + 初始化 retry_count=0)
  │
  ├─── route_by_intent == "complaint" ────► handle_complaint ────► END
  ├─── route_by_intent == "general_chat" ─► handle_general   ────► END
  └─── route_by_intent == "loan_consult" ─► retrieve_docs
                                                │
                                                ▼
                                          grade_retrieval (评估检索是否充分 + 改写查询 + retry_count+1)
                                                │
                                                ├─── is_sufficient == False 且 retry_count < 2 ──► 回跳 retrieve_docs 重试
                                                └─── is_sufficient == True 或 retry_count >= 2 ──► generate_loan_answer ──► END

```

---

## 二、 逐模块代码详解

### 1. 全局共享状态与结构化推理契约

```python
class DecisionState(TypedDict):
    user_query: str
    search_query: str
    intent: Literal["loan_consult", "complaint", "general_chat"]
    retrieved_docs: str
    is_sufficient: bool
    retry_count: int
    final_answer: str

```

* **`DecisionState`**：所有节点的“工作记忆”。每个节点只需返回它想更新的部分字段字典（如 `{"retrieved_docs": docs}`），LangGraph 会自动将其合并进全局状态。
* **`IntentDecision` 与 `RetrievalGrade**`：两个 Pydantic 模型配合 `llm.with_structured_output(...)`，把模型的意图分类、检索词改写和相关性判断固化为强类型字段，避免靠正则或文本解析猜测控制流。

---

### 2. 决策与执行节点（Nodes）

* **`classify_intent_node`（意图分类与查询标准化）**
调用 `IntentDecision` 解析 `user_query`，输出 `intent` 与初始 `search_query`，并将 `retry_count` 置 `0`。
* **`retrieve_docs_node`（动态知识库检索）**
读取 `state["search_query"]` 模拟检索结果：若命中 `"消费"`、`"装修"`、`"准入"` 等关键词返回信贷准入要点，否则返回未命中提示。真实工程中可将此处替换为向量数据库检索或混合检索接口。
* **`grade_retrieval_node`（检索质量评估与改写）**
对比 `user_query`、`search_query` 与 `docs`，输出 `is_sufficient`；若资料不足或过于宽泛，则生成更明确的 `rewritten_query`（如包含“个人消费贷款 准入 条件”），并将 `retry_count` 加 1。
* **`generate_loan_answer_node` / `handle_complaint_node` / `handle_general_node`（终态处理节点）**
* 贷款咨询走受控生成提示词，要求依据 `retrieved_docs` 作答且不编造利率或审批承诺；
* 投诉类直接给出转人工与优先核查响应；
* 闲聊类走简洁礼貌的通用回复。



---

### 3. 条件路由函数与图组装（Conditional Edges）

```python
def route_by_intent(state: DecisionState) -> str:
    if state["intent"] == "loan_consult":
        return "retrieve_docs"
    if state["intent"] == "complaint":
        return "handle_complaint"
    return "handle_general"


def route_after_grading(state: DecisionState) -> str:
    if state["is_sufficient"] or state["retry_count"] >= 2:
        return "generate_loan_answer"
    return "retrieve_docs"

```

* **`route_by_intent`**：在 `classify_intent` 之后根据 `intent` 分流，将不同类型请求导向各自的处理路径，避免闲聊或投诉误入贷款检索链路。
* **`route_after_grading`**：在 `grade_retrieval` 之后做闭环决策：
* 满足 `is_sufficient` 或达到 `retry_count >= 2` 时，停止重试并流转至 `generate_loan_answer`；
* 否则回跳至 `retrieve_docs`，用改写后的 `search_query` 再次检索。


* **环路终止保障**：`retry_count` 上限限制了最大重检次数，防止检索始终未命中时发生死循环。

### 4. 编译与运行测试

```python
app = workflow.compile()
result = app.invoke({"user_query": "我想借点钱搞家里翻新，有啥门槛？"})

```

* `workflow.compile()` 生成可执行的图应用 `app`。
* 传入初始字典 `{"user_query": ...}` 后，图自动沿节点和条件边推进，最终返回包含完整中间状态与 `final_answer` 的结果字典。

## 四、 工程实践中的可改进点

1. **避免重复计算 `retry_count**`：当前 `grade_retrieval_node` 每次执行都会 `retry_count + 1`；若首次检索即命中且 `is_sufficient=True`，`retry_count` 也会变成 `1`。语义上更清晰的写法是仅在“判定不充分准备重试”时递增，或在 `route_after_grading` 中明确区分“检索执行次数”与“重检次数”。
2. **接入真实检索与持久化检查点**：生产环境可将 `retrieve_docs_node` 接入 `VectorStore` 检索器，并在 `workflow.compile(checkpointer=...)` 中挂载 Checkpointer，以支持跨轮次状态恢复或人工审批挂起。
