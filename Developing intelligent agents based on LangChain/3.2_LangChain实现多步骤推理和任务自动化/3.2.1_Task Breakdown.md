Task Breakdown.py代码展示了一个**基于 LangChain LCEL（LangChain Expression Language）的“个人消费贷款咨询”结构化任务分解流水线**。代码顶部保留了最初的简化注释版本，下方则是完整的工程实现：它将原本笼统的单次或纯文本串联问答，拆解为“配置校验 → 结构化需求拆解 → 外部规则检索与上下文拍平 → 受控合规回复生成”四个职责独立的阶段。

---

## 一、 整体架构与数据流向

整条流水线的核心由 `task_decomposition_chain` 串联，输入与状态在管道中逐步丰富：

```text
{"query": "申请个人消费贷款需要满足哪些条件？"}
       │
       ▼  1. RunnablePassthrough.assign(analysis=analyze_chain)
{"query": "...", "analysis": LoanQueryAnalysis(...)}
       │
       ▼  2. context_builder (规则检索 + 嵌套字段拍平)
{"query": "...", "analysis": ..., "intent": "...", "loan_type": "...",
 "key_dimensions": [...], "missing_user_info": [...], "retrieved_rules": "..."}
       │
       ▼  3. answer_chain (answer_prompt | llm | StrOutputParser())
最终自然语言回复 (str)

```

---

## 二、 逐模块代码详解

### 1. 环境加载与模型初始化

```python
load_dotenv()
api_key = os.getenv("DASHSCOPE_API_KEY") or os.getenv("LLM_API_KEY")
if not api_key:
    raise ValueError("未检测到 DASHSCOPE_API_KEY 或 LLM_API_KEY，请在 .env 文件中配置。")

llm = ChatTongyi(
    model=os.getenv("LLM_MODEL_ID", "qwen-max"),
    dashscope_api_key=api_key,
    temperature=0.3,
)

```

* **环境变量兜底与校验**：同时兼容 `DASHSCOPE_API_KEY` 与自定义 `LLM_API_KEY`，缺失时立即报错（Fail-Fast），避免运行到模型调用阶段才抛出底层认证异常。
* **温度参数设置**：`temperature=0.3` 降低了生成随机性，适合结构化信息抽取和金融规则问答这类强调准确性与稳定性的场景。

---

### 2. 结构化数据契约（`LoanQueryAnalysis`）

```python
class LoanQueryAnalysis(BaseModel):
    intent: str = Field(description="用户核心意图，例如：查询准入条件、额度利率、申请材料或办理流程")
    loan_type: str = Field(description="贷款类别，例如：个人消费贷款")
    key_dimensions: list[str] = Field(description="需核查或解答的关键维度列表")
    missing_user_info: list[str] = Field(description="若要给出更精准评估，还需向用户确认的信息项")

```

* 使用 **Pydantic `BaseModel**` 定义第一阶段的输出数据结构，每个字段的 `Field(description=...)` 会被转换为底层 Schema 约束，指导模型按指定格式输出。
* 相比注释版里输出一段自由文本，这种方式为上下游节点建立了**强类型接口契约**。

---

### 3. 子任务一：结构化需求拆解（`analyze_chain`）

```python
analyze_prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个金融业务需求拆解助手..."),
    ("human", "用户请求：{query}"),
])
structured_llm = llm.with_structured_output(LoanQueryAnalysis)
analyze_chain = analyze_prompt | structured_llm

```

* **`with_structured_output(LoanQueryAnalysis)`**：将通用对话模型绑定为结构化输出模型，调用后直接返回 `LoanQueryAnalysis` 实例而非普通 `AIMessage`。
* **职责边界**：该子链只负责“理解用户想问什么、拆成哪些维度、还缺什么信息”，不直接编写对客回复。

### 5. 上下文组装与字段拍平（`context_builder`）

```python
context_builder = RunnablePassthrough.assign(**{
    "intent": RunnableLambda(lambda x: x["analysis"].intent),
    "loan_type": RunnableLambda(lambda x: x["analysis"].loan_type),
    "key_dimensions": RunnableLambda(lambda x: x["analysis"].key_dimensions),
    "missing_user_info": RunnableLambda(lambda x: x["analysis"].missing_user_info),
    "retrieved_rules": RunnableLambda(lambda x: retrieve_loan_rules(x["analysis"])),
})

```

* **`RunnablePassthrough.assign(...)`**：保留上游字典中已有的 `query` 和 `analysis`，同时向字典中增量写入新键值对。
* **字段拍平原因**：LangChain 的默认 `f-string` 提示模板不允许 `{analysis.intent}` 这类带点号的属性访问，因此这里把 `LoanQueryAnalysis` 对象的各个属性提取为顶层键（`intent`、`loan_type` 等），并同步调用 `retrieve_loan_rules` 注入 `retrieved_rules`。

> **代码整洁度提示**：紧挨着 `context_builder` 上方的 `def enrich_context(data: dict) -> dict:` 实现了完全相同的字典构造逻辑，但在后续链条中并未被调用（属于冗余代码），实际维护时可以删去，或直接写成 `RunnablePassthrough.assign(RunnableLambda(enrich_context))` 替代重复的 `lambda`。

---

### 6. 子任务三：受控最终回复生成（`answer_chain`）

```python
answer_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "你是一位严谨的个人信贷顾问。请严格依据提供的【准入规则参考】回答用户问题，"
        "不得编造具体银行利率或审批承诺；最后给出补充确认项与合规提示。"
    ),
    (
        "human",
        "原始问题：{query}\n拆解结果：...\n准入规则参考：\n{retrieved_rules}\n待确认信息：{missing_user_info}"
    ),
])
answer_chain = answer_prompt | llm | StrOutputParser()

```

* **角色与边界约束**：`system` 消息明确限定模型只能依据传入的 `retrieved_rules` 作答，禁止编造利率和审批承诺，有效降低金融场景下的模型幻觉风险。
* **多源信息融合**：`human` 消息同时接收原始问题（`query`）、结构化拆解结果（`intent`、`loan_type`、`key_dimensions`）、检索规则（`retrieved_rules`）以及待补充信息（`missing_user_info`），由 `StrOutputParser()` 提取纯文本作为最终输出。

---

### 7. 主链组合与执行入口

```python
task_decomposition_chain = (
    RunnablePassthrough.assign(analysis=analyze_chain)
    | context_builder
    | answer_chain
)

```

* 通过管道符 `|` 将三个子阶段声明式地组合为一个统一的 `Runnable` 对象，外部只需调用 `task_decomposition_chain.invoke({"query": user_query})` 即可触发完整的多步推理与检索流程。

## 三、 与顶部注释原版的核心差异对比

| 对比维度 | 顶部注释版 | 下方完善版 |
| --- | --- | --- |
| **阶段间数据格式** | 纯自由文本（`str`），靠提示词口头衔接 | `Pydantic` 结构化对象 + 字典状态累积，字段契约明确 |
| **外部知识引入** | 无，完全依赖模型内部参数记忆 | 引入 `retrieve_loan_rules` 规则检索步骤，回答有据可依 |
| **上下文保留** | 需手写 `lambda` 重组字典，原始 `query` 易丢失 | 使用 `RunnablePassthrough.assign` 自动保留历史字段 |
| **工程可控性** | 提示词泛化，容易发散或编造细节 | 拆解与生成分离，带系统级合规约束与环境变量校验 |
