User input triggers service.py代码使用 `RunnableWithMessageHistory` 为 LCEL 链接入了**按会话隔离的多轮对话历史记忆**，实现了具备上下文关联能力的客服对话触发流程。

---

### 一、 核心组件与执行流程

整个流程分为初始化、记忆管理、链包装与多轮触发四个阶段：

1. **环境与模型初始化**
* `load_dotenv()` 读取 `.env` 中的 `LLM_MODEL_ID` 和 `LLM_API_KEY`。
* `ChatTongyi` 初始化通义千问聊天模型（默认 `qwen-max`，`temperature=0.7`）。


2. **带历史占位符的 Prompt 模板（`prompt`）**
* 通过 `ChatPromptTemplate.from_messages` 组装三段消息结构：
* `("system", ...)`：设定客服助手角色定位。
* `MessagesPlaceholder(variable_name="history")`：动态注入过往的 `BaseMessage` 列表（`HumanMessage`、`AIMessage` 等），使模型看到完整对话轨迹。
* `("human", "{input}")`：接收当前轮次的用户输入。




3. **会话历史存储与检索函数（`store` 与 `get_session_history`）**
* 用字典 `store` 作为内存级会话存储，键为 `session_id`，值为 `ChatMessageHistory` 实例。
* `get_session_history(session_id)` 在首次访问某个 `session_id` 时创建新的 `ChatMessageHistory`，后续调用则返回同一份历史记录。


4. **记忆包装与多轮触发（`base_chain` 与 `conversation_chain`）**
* `base_chain = prompt | llm | StrOutputParser()` 负责单次提示词渲染、模型推理与文本解析。
* `RunnableWithMessageHistory` 将 `base_chain` 包装为带状态管理的执行器：
* `input_messages_key="input"`：指定当前轮次用户输入的字段名，执行后自动追加进历史记录。
* `history_messages_key="history"`：指定注入到 `prompt` 中 `MessagesPlaceholder` 的变量名。


* 在 `__main__` 中，通过 `config = {"configurable": {"session_id": "user_session_001"}}` 绑定会话 ID：
* **第一轮：** 输入 `"查询订单状态"`，模型引导提供订单号；本轮问答被写入 `user_session_001` 的历史。
* **第二轮：** 输入 `"我的订单号是 ORD-20260930-888，帮我看看进度"`，调用时自动把第一轮历史连同新输入一并送入模型，从而衔接上下文。

### 三、 潜在风险与改进点

* **进程内内存存储无法跨重启与多实例共享：** 当前 `store` 存放在内存中，服务重启会丢失全部会话；若部署多 worker/多节点，不同进程可能读不到同一份 `store`。生产环境可改用 Redis、SQLite/PostgreSQL 等持久化历史存储方案。
* **历史长度无裁剪易导致上下文膨胀：** 随着多轮对话变长，`history` 中的消息会持续累积，增加 Token 消耗、延迟甚至触及上下文上限。实际使用中常需配合消息条数截断、Token 预算控制或历史摘要压缩。
* **多用户并发需关注会话隔离与线程安全：** 务必确保每个用户/会话拥有独立的 `session_id`，切勿硬编码共享同一个 ID，否则会出现串话。
* **当前仅做对话承接，未接入真实订单查询：** 识别到 `ORD-20260930-888` 后，真实业务中通常需要进一步绑定查询工具或后端订单接口，获取真实状态后再由模型生成回复。
