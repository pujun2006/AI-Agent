Dynamic Task Scheduling Execution.py代码实现了一个基于 **LCEL** 的**客服意图识别与条件动态路由流水线**。它的核心思路是：先用大模型把用户问题归类为 `ORDER`、`LOGISTICS` 或 `OTHER`，再通过 `RunnableBranch` 把请求分发给对应的业务子链处理。

---

### 一、 核心组件与执行流程

整个链条按顺序经过四个阶段：

1. **环境与模型初始化**
* 调用 `load_dotenv()` 读取 `.env` 中的 `LLM_MODEL_ID` 与 `LLM_API_KEY`。
* 实例化 `ChatTongyi`（通义千问聊天模型），并将 `temperature` 设为 `0.1`。意图分类属于判别任务，低温度有助于减少随机输出，提高标签稳定性。
* 使用 `StrOutputParser()` 将模型返回的 `AIMessage` 解析为纯文本字符串。


2. **Step 1：定义业务子链（`order_chain`、`logistics_chain`、`default_chain`）**
* 每个子链都采用 `PromptTemplate | llm | output_parser` 的管道写法，分别对应订单查询、物流查询和通用客服。
* 它们接收包含 `query` 键的字典输入，拼接专属前缀提示词后调用大模型并返回文本结果。


3. **Step 2：定义意图分类链（`classifier_chain`）**
* 使用 `ChatPromptTemplate.from_messages` 构造包含 `system` 和 `human` 角色的消息模板。
* 系统提示词严格限定输出为 `ORDER`、`LOGISTICS`、`OTHER` 之一，并要求不输出多余文字，方便后续做字符串匹配。


4. **Step 3：构建条件动态路由（`RunnableBranch` 与 `full_router_chain`）**
* `full_router_chain` 左侧是一个并行字典映射 `{"topic": classifier_chain, "query": lambda x: x["query"]}`：当传入 `{"query": q}` 时，`topic` 会运行 `classifier_chain` 得到分类结果，同时 `query` 保留原始提问文本。
* 字典输出 `{"topic": "...", "query": "..."}` 随后流入 `RunnableBranch`。
* `RunnableBranch` 按顺序评估 `(条件函数, 执行分支)` 元组：命中第一个为真的条件即执行对应分支；若均不匹配，则执行最后一个位置参数传入的默认兜底分支（`default_chain`）。


5. **Step 4：批量测试运行**
* 在 `__main__` 中遍历 3 条测试query，依次调用 `full_router_chain.invoke({"query": q})` 并打印分类后的业务处理结果。

### 三、 潜在风险与改进点

虽然这段代码结构清晰、适合入门演示，但在实际业务中仍有几个值得注意的细节：

* **关键词包含匹配存在歧义：** 当前判断条件是 `"ORDER" in x["topic"].upper()`。如果模型偶尔输出包含 `ORDER` 的解释性句子，或同时出现两个词，可能触发非预期分支。更稳妥的做法是做 `.strip().upper()` 精确匹配或正则提取。
* **意图边界重叠：** 例如第一条测试 query 同时提到“订单 ORD-8899”和“到哪里了、快递单号”，模型有时可能在 `ORDER` 与 `LOGISTICS` 之间摇摆，需要在系统提示词中明确主次判定规则。
* **重复调用与多余导入：** 代码中导入了 `RunnableLambda`，但实际使用的是 `lambda x: ...`（在 LCEL 字典与 `RunnableBranch` 中会自动转换为 `RunnableLambda`）；此外 `branch` 里的分支函数又调用了 `.invoke(...)`，若改用 `RunnablePassthrough` 传递字段会让声明式写法更统一。
* **确定性业务可直接接接口：** 示例中的 `order_chain` 和 `logistics_chain` 只是加上了文本前缀；真实系统中，识别出 `ORDER` 或 `LOGISTICS` 后，通常应先调用订单/物流查询工具或 API 获取真实数据，再交给 LLM 润色回复。
