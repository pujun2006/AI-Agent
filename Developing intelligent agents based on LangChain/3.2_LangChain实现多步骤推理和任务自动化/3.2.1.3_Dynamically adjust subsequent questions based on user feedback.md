Dynamically adjust subsequent questions based on user feedback.py代码实现了一个**基于状态评估与结构化决策的多轮动态追问会话系统**（以个人消费贷款需求澄清为例）。它与前面固定顺序或并行拆解的链不同，核心特点是**每轮根据历史对话与最新用户反馈，动态判断信息是否足够，决定是“继续针对性追问”还是“收敛输出方案”**。

---

## 一、 核心运行机制：评估 → 决策 → 追问/收敛闭环

整套交互并非写死“第 1 问金额、第 2 问用途、第 3 问期限”，而是围绕 `FollowUpDecision` 形成动态闭环：

```text
用户本轮输入 (user_feedback) + 历史对话 (chat_history)
       │
       ▼  decision_chain (ChatPromptTemplate + with_structured_output)
FollowUpDecision {
  is_complete,               # 信息是否足够收敛
  known_facts,               # 已确认事实
  missing_or_unclear_points, # 仍缺失或模糊的点
  next_question,             # 动态生成的下一步追问
  summary_or_advice          # 信息充分时的初步建议
}
       │
       ├─── is_complete == False 且未达 max_turns ──► 输出“已确认 + next_question”，继续下一轮
       │
       └─── is_complete == True 或达到 max_turns ────► 调用 _build_final_response 输出方案并结束

```

## 二、 逐模块代码详解

### 1. 环境初始化与模型配置

```python
load_dotenv()

api_key = os.getenv("DASHSCOPE_API_KEY") or os.getenv("LLM_API_KEY")
if not api_key:
    raise ValueError("未检测到 DASHSCOPE_API_KEY 或 LLM_API_KEY，请在 .env 文件中配置。")

llm = ChatTongyi(
    model=os.getenv("LLM_MODEL_ID", "qwen-max"),
    dashscope_api_key=api_key,
    temperature=0.3,
)

```

* 兼容 `DASHSCOPE_API_KEY` 与 `LLM_API_KEY`，缺失时立即终止，避免进入多轮调用后再报认证错误。
* `temperature=0.3` 保持信息提取与追问策略相对稳定，减少模型在多轮交互中“跑题”或随意改变判断标准的概率。

---

### 2. 动态决策数据结构（`FollowUpDecision`）

```python
class FollowUpDecision(BaseModel):
    is_complete: bool = Field(...)
    known_facts: list[str] = Field(...)
    missing_or_unclear_points: list[str] = Field(...)
    next_question: str = Field(...)
    summary_or_advice: str = Field(...)

```

这是实现“动态调整”的关键契约：

* **`is_complete`**：充当流程控制开关，决定会话是继续追问还是进入最终方案输出。
* **`known_facts` 与 `missing_or_unclear_points**`：显式追踪“已掌握什么、还缺什么、哪项表述含糊”，让每一轮追问都有依据，避免重复提问或遗漏关键要素。
* **`next_question`**：根据当前缺口动态生成的单轮追问话术。
* **`summary_or_advice`**：当信息满足要求时直接承载阶段性方案与合规说明。

---

### 3. 动态追问决策链（`decision_chain`）

```python
decision_prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一位专业、耐心的信贷需求顾问..."),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "用户最新反馈：{user_feedback}"),
])

structured_decision_llm = llm.with_structured_output(FollowUpDecision)
decision_chain = decision_prompt | structured_decision_llm

```

* **`MessagesPlaceholder(variable_name="chat_history")`** 是多轮对话的核心组件，它会在运行时把 `self.chat_history` 中的 `HumanMessage` 和 `AIMessage` 列表原封不动展开插入到系统提示词与当前用户输入之间，使模型感知完整上下文。
* **策略约束写在 `system` 指令中**：
1. 每次只聚焦 `1~2` 个最关键的缺失点或模糊反馈，避免一次性抛出一长串问题给用户造成压迫。
2. 当用户说“不确定/大概/先看情况”时，顺着反馈降低门槛或提供折中选项，而不是生硬要求精确数字。
3. 严禁编造具体利率或审批承诺，并对资金用途做合规提示。



---

### 4. 会话状态控制器（`DynamicInquirySession`）

这个类把**状态管理**和**流程控制**从模型调用中抽离出来，方便接入 CLI、Web 接口或前端状态机：

* **状态字段**：
* `chat_history`：保存历史 `HumanMessage` 与 `AIMessage`。
* `max_turns` 与 `turn_count`：控制最大追问轮次，防止用户始终模糊作答时陷入死循环。
* `latest_decision`：缓存最近一轮的 `FollowUpDecision` 对象，便于外部代码读取结构化状态（例如判断是否 `is_complete` 或展示已提取要素）。


* **核心流转方法 `step(user_feedback)**`：
1. 轮次计数加 1，调用 `decision_chain` 传入 `chat_history` 和 `user_feedback` 得到 `decision`。
2. 将本轮 `HumanMessage(content=user_feedback)` 追加进 `chat_history`。
3. 若 `decision.is_complete` 为真，或 `self.turn_count >= self.max_turns`，调用 `_build_final_response(decision)` 生成最终回复并写入历史后返回。
4. 否则拼接“已确认要点 + `next_question`”作为本轮助手回复，存入 `chat_history` 并返回。


* **总结兜底 `_build_final_response**`：
* 优先复用 `decision.summary_or_advice`；若模型在 `is_complete=True` 或达到 `max_turns` 时该字段为空，则自动启用 `fallback_chain` 结合对话历史与 `known_facts` 生成一份合规的初步建议，保证最终输出不为空。

```python
if __name__ == "__main__":

    simulated_user_inputs = [

```

* 通过预设的三段递进式用户输入模拟真实多轮沟通：第一轮需求笼统 → 第二轮给出大致金额与装修用途但预算未定 → 第三轮补充职业、税后收入、社保与期望期数。
* 实际部署时，只需把 `simulated_user_inputs` 的循环替换为 `while True: user_input = input("用户：")` 或 Web/IM 会话接口即可。

## 四、 实际落地时的可优化点

1. **历史记录顺序细节**：在当前 `step()` 中，调用 `decision_chain` 之后才 `self.chat_history.append(HumanMessage(content=user_feedback))`，因此 `chat_history` 传入的是“本轮之前的历史”，而本轮输入通过 `("human", "用户最新反馈：{user_feedback}")` 单独传入，这样设计避免了当前输入被重复放进历史占位符；若后续引入记忆裁剪（如只保留最近 N 轮消息），需注意与 `turn_count` 配合使用。
2. **结合外部知识/规则引擎**：当 `is_complete=True` 准备输出方案时，可在 `_build_final_response` 前接入前面提到的规则检索或产品匹配逻辑，使建议更贴合具体业务规则。
3. **升级为持久化图状态**：若需要跨请求重启恢复会话、保存检查点或做更复杂的分支回退，可将 `DynamicInquirySession` 的状态结构迁移至 `LangGraph`。
