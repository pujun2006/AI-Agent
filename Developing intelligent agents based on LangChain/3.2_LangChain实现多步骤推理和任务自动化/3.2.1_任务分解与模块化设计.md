LangChain 的核心设计思想是将复杂的大语言模型（LLM）应用拆解为**高内聚、低耦合、可组合的标准化模块**，并通过统一的编排机制将子任务连接起来，从而兼顾开发效率、可维护性与生产级扩展能力。

---

## 一、 模块化架构：分层解耦与 Runnable 契约

现代 LangChain 将生态划分为清晰的包层级，避免单一巨型依赖带来的膨胀与冲突：

* **`langchain-core`**：定义最基础的抽象与协议，包括消息类型（Messages）、提示模板（Prompts）、输出解析器（Output Parsers）以及核心的 **Runnable** 接口。
* **专属集成包（如 `langchain-openai`、`langchain-anthropic`）**：封装特定厂商的模型或服务 SDK，使切换模型或向量库只需替换局部组件。
* **`langchain-community`**：容纳大量社区维护的三方工具、文档加载器、数据源与向量数据库接口。
* **`LangGraph` 运行时**：提供有状态图编排、检查点持久化（Checkpointer）、循环控制与多智能体协作能力，现代 Agent 也建立在其底层运行时之上。

### 统一契约：Runnable 与 LCEL

为了让不同模块像乐高积木一样无缝拼接，核心组件均实现统一的 **Runnable** 接口，提供一致的同步/异步调用方式（如 `invoke` / `ainvoke`、`stream` / `astream`、`batch` / `abatch`）。在此基础上，**LCEL**（LangChain Expression Language）允许通过管道符（`|`）等声明式原语组合组件，自动获得流式输出、并发执行和链路追踪能力。

## 二、 核心功能模块划分

LangChain 把端到端应用拆分为职责明确的独立模块，便于单独测试、替换与复用：

| 模块类别 | 核心职责 | 典型能力 / 原语 |
| --- | --- | --- |
| **模型与向量接口** | 统一不同大语言模型与嵌入模型的调用方式，屏蔽底层 API 差异 | ChatModel、Embeddings、结构化输出绑定 |
| **提示工程模块** | 管理变量注入、角色指令与少样本上下文，将业务规则与代码分离 | `ChatPromptTemplate`、消息占位符、模板复用 |
| **数据接入与检索** | 完成外部非结构化数据的加载、切分、索引与相关性召回 | Document Loaders、Text Splitters、VectorStores、Retrievers |
| **输出解析与校验** | 将模型自由文本转换为结构化数据或特定格式，降低下游解析成本 | `StrOutputParser`、Pydantic / JSON 解析器 |
| **工具与记忆状态** | 赋予系统调用外部系统及跨轮次、跨步骤保留上下文的能力 | `@tool` 工具定义、短期/长期记忆、LangGraph 状态与检查点 |

## 三、 任务分解的三种核心范式

面对复杂业务需求，LangChain 支持从**确定性流水线**到**动态自治与多角色协作**的不同分解层级：

### 1. 静态流水线分解（LCEL 链式与拓扑编排）

当任务步骤相对固定、前后依赖明确时，可将任务拆分为线性或有向无环的子步骤：

* **串行拆解**：例如“查询改写 → 文档检索 → 上下文拼接 → 答案生成 → 格式解析”，每一步只关注单一转换。
* **并行与分支拆解**：借助 `RunnableParallel` 同时执行多路检索或独立分析以降低延迟；借助 `RunnableBranch` 根据意图或条件路由到不同子链；借助 `RunnablePassthrough` 在流转中保留原始输入。

### 2. 动态自主分解（Agent 与工具调用循环）

当事前无法穷举所有执行路径、需要根据中间结果决定下一步动作时，由大模型充当推理控制器：

* 模型根据目标与可用 **Tools**（如搜索、数据库查询、代码执行、业务 API）拆解行动，输出工具调用请求。
* 框架执行工具并将返回结果回传给模型，形成“推理 → 选工具 → 执行 → 观察结果”的循环，直至得出最终回答。

### 3. 图状态与多智能体分解（LangGraph 协同）

对于长链路、允许回溯重试或需要人工介入的复杂任务，单次线性链或单一循环往往难以治理，此时通过显式 **State（状态）** 与 **Graph（节点与边）** 进行结构化分解：

* **状态隔离与演进**：各节点读取共享状态中的特定字段并增量更新，避免长上下文互相覆盖。
* **角色分工**：在多智能体架构中，可将任务拆分为 **Planner**（拆解子任务与规划顺序）、**Executor**（执行检索、写代码、翻译等专职工作）、**Reviewer**（校验质量并在不达标时打回重做）等节点。

## 四、 工程实践要点

* **按需选择粒度**：能用单次模型调用或简单 LCEL 流水线解决的任务，不必强行引入多智能体或复杂图编排；过度拆分会增加延迟、Token 消耗与调试难度。
* **明确模块边界与状态契约**：每个子步骤的输入、输出字段与异常回退策略应清晰可控，方便针对单个节点做单元测试与评估。
* **配合可观测性工具**：在多步分解与工具调用场景下，结合链路追踪工具（如 LangSmith）观察每一步的输入输出与耗时，是定位幻觉、死循环或瓶颈的关键。
